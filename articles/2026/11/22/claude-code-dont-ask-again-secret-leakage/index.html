Функцията „Don't Ask Again“ в Claude Code излага десетки хиляди тайни и API ключове в публични хранилища

Публикувано от Svetni.me Editorial на 22 ноември 2026 г. в Изкуствен интелект


Снимка: Wikimedia Commons / InfoQ

Според репортаж на InfoQ компанията за сигурност на агентни системи Apiiro е установила, че инструментът за програмиране Claude Code на Anthropic масово излага чувствителни тайни в публични хранилища поради начина, по който съхранява локалните конфигурации за функцията „Don't Ask Again“ („Не питай отново“) [1].

Първоначалното проучване на Apiiro идентифицира 1122 тайни във файлове claude/settings.local.json и още 1160 в Git историята, в споделени файлове settings.json и в транскрипти от чатове с агенти, засягайки общо 63 организации. Последващ анализ на GitGuardian разкрива още по-голям мащаб на проблема — 31 088 тайни във файлове .claude/settings.local.json в публичния GitHub, от които 5343 са били все още валидни към момента на засичането, както и допълнителни 613 тайни в контейнери в Docker Hub [1].


Инфографика: Светни.ме

Механизъм на уязвимостта в .claude/settings.local.json

Проблемът произтича от начина, по който Claude Code управлява одобрението на терминални команди. Когато разработчикът избере опцията „Yes, and don’t ask again“, за да разреши изпълнението на дадена shell команда, агентът записва цялата команда като постоянно правило за достъп в локалния конфигурационен файл .claude/settings.local.json. Ако командата съдържа вградени пароли, облачни API ключове, производствени токени за достъп или npm токени, те се записват в чист текст [1].

Защитният механизъм на инструмента има критичен архитектурен пропуск при работа със системата за контрол на версиите [1]:

  • Разчитане само на глобален gitignore: Когато Claude Code създава файла вътре в съществуващо Git хранилище, той го добавя единствено в глобалния списък за игнориране на конкретния компютър на разработчика, но не и в собствения .gitignore файл на проекта.

  • Липса на преносима защита: Тъй като правилото не пътува заедно с хранилището, файлът остава незащитен, ако директорията бъде инициализирана като Git репо на по-късен етап, при клониране на друга машина или ако вече е бил добавен от друг член на екипа. В някои случаи изследователите установяват, че самият Claude Code е извършил git commit на конфигурационния файл.

  • Заобикаляне на стандартните скенери за тайни: Популярни инструменти за сканиране като gitleaks и TruffleHog не успяват да засекат всички изтекли данни, тъй като са настроени да търсят стандартни формати на ключове, а не пароли, вградени като аргументи вътре в shell команди. Същият модел на изтичане се наблюдава и в транскрипти, файлове за памет и бележки за предаване на задачи (handoff notes) между агенти.

Системни последици за сигурността на ИИ агентите за програмиране

Откритията на Apiiro и GitGuardian около Claude Code, наред с предишни предупреждения за сходни рискове при Cursor и GitHub Copilot, очертават нов клас заплахи в сигурността на софтуерната развойна среда:

  • Предвидима мишена за локален зловреден софтуер (Malware Target): Както отбелязват изследователите от Apiiro, дори когато файлът .claude/settings.local.json не бъде качен в GitHub, той представлява сериозен локален риск. За всеки зловреден софтуер на машината на разработчика този файл е готов каталог на всички системи, до които разработчикът има достъп, заедно с паролите за тях — винаги разположен на един и същ стандартен път във всеки проект.

  • Изолация на контекста чрез MCP сървъри: В отговор на тези рискове част от инженерната общност преминава към пълно премахване на локалните конфигурационни и паметови ИИ файлове (settings.local.json, CLAUDE.md, AGENTS.md) от програмните хранилища, изнасяйки управлението на паметта, задачите и документацията към външни сървъри чрез протокола Model Context Protocol (MCP).

  • Задължителни мерки за хигиена на хранилищата: Експертите на Apiiro препоръчват незабавно прекратяване на проследяването на файла чрез командата git rm --cached .claude/settings.local.json, изричното му добавяне в локалния .gitignore на хранилището и пълна ротация на всички ключове и пароли, които някога са присъствали в него. Като фундаментално правило разработчиците трябва да подават секретни данни към агентни команди единствено чрез променливи на средата (environment variables), вместо да ги изписват директно в командния ред [1].
